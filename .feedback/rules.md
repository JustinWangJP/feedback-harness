  <sub>出典: 20260812-213958 (2026-08-16 昇華)</sub>

### 再現すべき措辞・進め方(成功由来)

- **[workflow]** 依存パッケージ・ツールを推奨する前に、レジストリで素性を確認する(npm view の description・repository・maintainers・最終更新・DL数)。同名の偽パッケージや中身の無い名前予約が実在し、確認無しの推奨は無関係・有害な実装の導入を招くため。  
  <sub>出典: 20260816-232833-3 (2026-08-19 昇華)</sub>

- **[style]** 文書の「校正」を依頼されたときは、構成と情報量を維持し、言語面のわかりにくさ(長文・曖昧な主語・無注釈の専門用語・直訳調)だけを平易で自然な表現へ直す。依頼者が求めているのは文面の改善であり、内容の追加・削除や構成変更は別種の作業で明示的な許可が要るため。  
  <sub>出典: 20260819-231838 (2026-08-19 昇華)</sub>

- **[workflow]** 文書作業は「校正(文言のみ・内容維持)」と「監査・改稿(実装・公式仕様との照合、更新・追加・削除)」の別種タスクとして区別し、依頼されたのがどちらかを確認してから着手する。範囲の指示が競合するときは最新の明示指示を優先する(以前の制約は明示的な許可で更新される)。2つは確認対象と変更権限が異なり、混ぜると許可外の変更や監査漏れにつながるため。  
  <sub>出典: 20260819-233628 (2026-08-19 昇華)</sub>

- **[architecture]** OS・実行環境の対応を足すときは、既存の資産をそのまま動かせる互換層(Windows なら Git Bash 等)を優先し、その環境専用の実装を増やさない。専用実装は同じ機能の二重管理になり、片方だけ直る形でドリフトするため。<br>
  <sub>出典: 20260823-221316 (2026-08-26 昇華)</sub>
