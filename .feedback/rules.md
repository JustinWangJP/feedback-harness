### 守るべき制約(失敗由来)

- **[style]** 設定値・URL・パスはハードコードせず設定ファイル/環境変数から読む。環境差で壊れるため。  
  <sub>出典: 20260809-163042 (2026-08-09 昇華)</sub>

- **[style]** ID・キーの照合は部分文字列一致ではなく厳密一致(完全一致、または区切り文字まで含めた境界一致)で行う。枝番ID(X と X-2)のようにプレフィックスを共有するキーへ誤ヒットし、別対象の誤更新・誤削除という静かな誤動作になるため。  
  <sub>出典: 20260812-213958 (2026-08-16 昇華)</sub>

- **[architecture]** 処理を省略する最適化(変更が無いときのスキップ等)を入れるときは、スキップ判定が取りこぼす変更種別(削除・改名・権限変更など)を列挙して検証する。判定を誤る場合は安全側(常に実行する)に倒す。スキップ最適化は『速いが不正確』へ倒れやすいため。  
  <sub>出典: 20260812-220600 (2026-08-16 昇華)</sub>

- **[testing]** 検証対象の機構を、そのテスト自身の合否判定に使わない。判定機構が壊れるとテストが無条件成功する最悪の壊れ方を自己検出できなくなるため。テストランタイムの健全性を検証する土台テストは独立した判定(自前カウンタ+明示exit)とし、変異テストで壊れたときに気づれることを確認する。  
  <sub>出典: 20260812-220600-2 (2026-08-16 昇華)</sub>

- **[workflow]** ツール・ライブラリの未導入を発見しても、インストールを勝手に実行・確定しない。何を・どの手段で入れるかを提示してユーザーの許可を得てから実行する。インストールはユーザーの環境を変更する行為で、同意なく実行すれば環境を壊し信頼を損なうため(ハーネスの検査も npx --no-install でこの原則を守る)。  
  <sub>出典: 20260816-232833 (2026-08-19 昇華)</sub>

- **[architecture]** ツールの導入手段はOS依存の手段(brew 等)を既定にしない。横断ツールは言語エコシステムのパッケージマネージャ(npm/pip/go/cargo 等)、スタック固有の検査はそのスタックのパッケージマネージャで導入できるものを優先する。OS依存の手段は導入先の環境次第で欠け、配布物の再現性を壊すため。  
  <sub>出典: 20260816-232833-2 (2026-08-19 昇華)</sub>

- **[architecture]** パッケージマネージャ固有のコマンド(npm ls --all / npm audit / npx 等)をスクリプトへ足すときは、PM・lockfile 判定をスクリプト毎に書き足すのではなく一箇所の共通関数へ集約し、npm 以外は理由付きSKIPとする。追加前に既存スクリプトへ同じコマンドの前例が無いか grep して確認する。判定の書き忘れは pnpm/yarn プロジェクトでの誤FAIL(ENOLOCK 等)として同じ欠陥を再発させるため。  
  <sub>出典: 20260817-142537 (2026-08-19 昇華)</sub>

- **[workflow]** 複数の実行環境(Claude Code / Codex app・CLI / IDE拡張 / 汎用エージェント)へ配る手順を案内するときは、まず現在の実行環境を確認し、その環境で不要な作業を必須として提示しない。案内文・停止メッセージにも環境別の要否を明記する。環境を確認せず一律に案内すると、その環境では不要な手作業を利用者へ強いることになるため。  
  <sub>出典: 20260820-000443 (2026-08-22 昇華)</sub>

- **[architecture]** 複数の配布物(スキル・エージェント定義・README各言語版・ポインタ文書・CLI実装)が共有する分類語彙や列挙定義を追加・変更するときは、参照している全ファイルを同じ変更で更新し、整合を検証するテストを併せて追加する。定義は文書とコードへ分散して複製されるため、片方だけの更新は判定基準のずれとして残り、レビューでしか気づけないため。  
  <sub>出典: 20260820-000519 (2026-08-22 昇華)</sub>

- **[testing]** テストや lint が「ある」ことを根拠に「その欠陥は防がれている」と結論しない。当該テストのアサーションを実際に読み、問題のケース(境界・併存・異常系)を検証しているか確認してから現状追認を判断する。ファイル名や冒頭コメントの主張と実際の検証範囲はずれるため、存在確認だけの追認は欠陥を素通りさせる。  
  <sub>出典: 20260822-164358 (2026-08-22 昇華)</sub>

- **[architecture]** 意味の判断が要る処理(類似・重複・関連の判定など)を、文字列一致や類似度しきい値といった機械的heuristicで代替しない。CLI・スクリプトは調査対象を漏れなく列挙する役に徹し、判定はエージェントが本文を読んで行う契約にする。しきい値は言語・書式・語彙で分布が変わり(実測: 英語は無関係な2文でも0.16、中国語は同主題でも0.10)、特定言語でしか機能しない足切りとして静かに取りこぼすため。  
  <sub>出典: 20260822-172600 (2026-08-22 昇華)</sub>

- **[testing]** 配布物をCIでlintするときは、開発機の新しいlintバージョンでの成功だけを互換性の根拠にせず、CI・配布先でサポートする最低バージョンでも検証する。診断規則やsource解析はバージョンで変わり、ローカルだけでは配布先での失敗を事前検出できないため。<br>
  <sub>出典: 20260822-232342 (2026-08-23 昇華)</sub>

### 再現すべき措辞・進め方(成功由来)

- **[workflow]** 依存パッケージ・ツールを推奨する前に、レジストリで素性を確認する(npm view の description・repository・maintainers・最終更新・DL数)。同名の偽パッケージや中身の無い名前予約が実在し、確認無しの推奨は無関係・有害な実装の導入を招くため。  
  <sub>出典: 20260816-232833-3 (2026-08-19 昇華)</sub>

- **[style]** 文書の「校正」を依頼されたときは、構成と情報量を維持し、言語面のわかりにくさ(長文・曖昧な主語・無注釈の専門用語・直訳調)だけを平易で自然な表現へ直す。依頼者が求めているのは文面の改善であり、内容の追加・削除や構成変更は別種の作業で明示的な許可が要るため。  
  <sub>出典: 20260819-231838 (2026-08-19 昇華)</sub>

- **[workflow]** 文書作業は「校正(文言のみ・内容維持)」と「監査・改稿(実装・公式仕様との照合、更新・追加・削除)」の別種タスクとして区別し、依頼されたのがどちらかを確認してから着手する。範囲の指示が競合するときは最新の明示指示を優先する(以前の制約は明示的な許可で更新される)。2つは確認対象と変更権限が異なり、混ぜると許可外の変更や監査漏れにつながるため。  
  <sub>出典: 20260819-233628 (2026-08-19 昇華)</sub>
