## curator の反映先選択契約

`context` と `failure / 文脈欠落` のどちらでも、まず導入先の AGENTS.md / CLAUDE.md と、その文書が参照する共通規約・前提情報の文書を確認する。ファイル名だけで正本を決めず、明記された役割と参照関係から選ぶ。

| 導入先の状態 | 追記案の作り方 |
|---|---|
| 共通規約と参照文書が明示されている | 行動制約は共通規約、前提知識・背景は役割に合う参照文書へ提案。必要なら共通規約からの読取案内も提案する |
| AGENTS.md だけがある | その文書と参照先を確認して選ぶ。CLAUDE.md の新設を前提にしない |
| CLAUDE.md だけがある | その文書と参照先を確認して選ぶ。AGENTS.md の新設を前提にしない |
| 両方あるが正本が不明・矛盾している | 両方へ同じ内容を追記しない。候補・参照関係・判断できない点を提示して反映先の裁定を求める |
| どちらもない | 既存の開発規約・参照資料を探し、候補を示す。固定名への無断作成はしない |

提案には対象パス、節、追加内容、選定理由、入口からの参照経路を含める。既存の `automation_candidates` 出力契約との対応を確認し、必要な補足を揃える。`.feedback/rules.md` 以外は提案を提示して承認後に反映する既存の境界を維持する。

`instruction` / `workflow` の成功セクションへの promote、失敗の根因別反映先、重複時の merge、再発時のルール強化、retire と出典・status 更新は維持する。rules.md の手編集による統合は行わない。共通規約への移行を理由にルールを無断で削除・退役しない。

後続実装では curator 定義と [feedback-loop スキル](../../skills/feedback-loop/SKILL.md) を中心に、共有成果物の追記先・入力・出力を案内する他のスキルや文書も走査し、同じ契約の記載だけを同期する。配布用テンプレートと init.sh の構成変更へ範囲を広げない。

4. 全項目の移行を確認した後、CLAUDE.md を正本の読取指示と環境固有の補足へ縮小する。共通規約を二重に維持しない。
5. curator と関連スキルの反映先選択契約を更新する。上表の導入先ケースで、反映案と参照経路をレビューする。
6. 新設文書を README の構成ツリー・文書索引の各言語版に反映する。履歴資料には既存形式の注記を付け、現在の規約と区別する。
7. 以下の自動検査と本文レビューを実施し、対応表に実際の移行先の節を記録する。失敗を修正してから移行完了とする。

## 再発防止と後続実装の受け入れ条件

| 確認対象 | 自動検査で確かめること | 本文レビューで確かめること |
|---|---|---|
| 正本への参照切れ | CLAUDE.md の正本参照、参照先ファイル・アンカーの存在、文書索引との整合 | 入口から正本、必要な資料へ辿って読む指示として明確で、循環がない |
| 必須規約の移行漏れ | 起点の旧項目を列挙し、対応表の欠番・未割当・移行先不在を検出する | 全項目の意味、例外、適用条件が保持され、背景文書だけに必須制約が隠れていない |
| CLAUDE.md への再蓄積 | 旧共通節の残存や想定外の新節をレビュー対象として検出する | 各追記が Claude Code に固有か判断し、共通制約なら正本へ反映する |
| curator の経路 | 関連配布物から追記先を固定した記載を列挙し、契約の更新漏れを確認する | 片方の文書しかないケースを含め、役割に沿う提案先・理由・参照経路になっている |
| rules の既存経路 | 関連する既存 CLI・スキル整合テストを実行する | promote / merge / retire、承認境界、出典管理を変えていない |

機械検査の期待集合は旧本文・実ファイル・参照元から導出する。走査の終了コードと実対象を検出したことを確認し、参照削除・移行先削除などの欠陥再注入で検出できることを検証する。変異は隔離コピーで行うか退避した内容から復元し、未コミット変更を破棄しない。

文字列の存在は、意味の保存や実際の読取の証明にはならない。Codex / 汎用エージェントの AGENTS.md 入口と Claude Code の CLAUDE.md 入口から、同じ作業例（テストの起動、前提知識の追記提案、完了前チェック）を辿り、必要な規約と判断が揃うかレビューする。読取を実環境で確認していない場合は未検証として記録する。

移行完了には、対応表全件の本文照合、リンク・索引検査、関連テスト、`git diff --check`、リポジトリ所定の `bash scripts/check.sh` の exit 0 が必要である。WARN / SKIP の内容も確認し、意味の共有を文字列検査だけで合格扱いしない。

## 今回の計画書作成の検証・完了条件

- 新ブランチの HEAD が取得した `origin/main` と起点コミットに一致することを確認する。
- 追跡差分と未追跡ファイルを両方確認し、変更が本計画書と既存規約上必要な文書索引だけであることを確認する。
- 本計画書を明示的に対象に含めて文書リンク検査を実行する。未追跡ファイルを git 追跡対象だけの走査で検証済みと扱わない。
- `git diff --check` と新規ファイルの空白検査を行う。
- リポジトリ所定の完了前チェック `bash scripts/check.sh` を新worktreeで実行し、exit 0 と WARN / SKIP の理由を確認する。
- 最終報告にブランチ名、worktree、計画書の場所、検証結果を記載する。コミット・プッシュは行わない。
