## 2. 提案機能(P1–P5)

### P1. フック成果物ログ + `stats` サブコマンド — 「効いているか」を測る

**記事根拠**: L69(初回通過率・イテレーション数)、L71(DORA 指標の先行信号)、L73(仪表盘を建てない — **テキスト出力のみとする制約**)

ハーネスはすでに「AI の初回出力の質」を観測できる唯一の位置にいる: PostToolUse と Stop の合否である。これを記録し、集計する。

実装概要:

- `post_edit.sh` / `on_stop.sh` が結果を `.feedback/events.jsonl` に1行追記する
  (`{"ts": "...", "hook": "post_edit", "file": "...", "result": "pass|fail"}`)。成功時も失敗時も記録する(現状は失敗しか見えない)
- ローテーション: サイズ上限(例: 512KB)で末尾N行に切り詰め。**gitignore 対象**とし、共有されるのは集計結果だけにする
- `feedback_log.py stats` — テキスト出力:
  - フック系: PostToolUse 初回通過率(ファイルごとの初回チェック合否率)、1ファイルあたりの平均再チェック回数(イテレーション数の代理)、Stop フルチェックの初回通過率、失敗上位のファイル・ツール
  - ログ系: source / category / 根因 别件数、open エントリの経過日数(最古・3件超の通知)、promote 率
  - **再発候補**: promote 済みルール(出典id・昇華日付き)の昇華日以降に同 category のエントリがあれば「ルールが効いていない候補」として列挙 — curator 原則5・Phase 4 手順1の手動検索を機械化する

**実装上の前提(2026-08-16 確認済み)**: `harness_tree_changed` は `.feedback/` を丸ごと prune する(`scripts/lib.sh:75-78`)ため、`events.jsonl` の更新が木変更判定に影響することはない。ただしこの前提は P1 の寿命を支えるものであるため、**「`.feedback/` 内のファイル更新でフルチェックが走らない」ことを固定する回帰テスト**を追加する(prune 縮小・条件変更で壊れたら直ちに気づけるように)。

規模: 中(スクリプト2本への追記 + CLI 1サブコマンド + テスト)。
軽量性: ✔ 出力は要求時のテキストのみ。常駐プロセス・グラフ・外部保存なし。

### P2. `report` サブコマンド — 朝会・振り返りの議題ダイジェスト

**記事根拠**: L55(朝会の1問「昨日 AI で何か発見あった?」)、L57(振り返り=個人観察をチーム決定に変える場。産出は具体的であるべき)、L61(最重のリズムでも既存会議+5分)

P1 の数字と既存の `.feedback/` データから、期間区切りの Markdown ダイジェストを生成する。「もう一つの会議」を作らず、既存の朝会・振り返りに貼る5分議題を供給する部品。

実装概要:

- `feedback_log.py report --since <YYYY-MM-DD | yesterday | --last>`
  - 新規エントリ(category / 根因 / source グループ別)
  - 昇華・統合・退役の履歴(promote 日は rules.md の出典行から、retire/close はエントリ本文の追記から復元。正確な時刻が必要なら frontmatter への `promoted_at` 等の小幅追加も可)
  - open 棚卸し(滞留年齢)と再発候補(P1 の機械化を流用)
  - P1 導入後は初回通過率トレンド
- `--last` は `.feedback/.last-retro` スタンプで「前回の振り返り以降」を指す(振り返りのたびに更新)。朝会モードは `--since yesterday`
- 出力イメージ(5分議題): *この期間で増えた信号 / 昇華したルール / 再発=ルール強化候補 / open の滞留 / 数字の向き*

規模: 小〜中(CLI 1サブコマンド + スタンプファイル)。
軽量性: ✔ ダイジェストは既存の儀式に差し込むもので、新規ミーティングを作らない。

### P3. シグナル型の第一級化 — 4分類をデータにする

**記事根拠**: L37–47(四种信号、「信号与制品之间的映射关系是具体的」)、L41(指令信号=個人熟練とチーム能力の差)

現状の軸は category(ドメイン別)と根因(失敗系のみ・`--detail` の自由文)。記事の4分類(上下文/指令/工作流/失敗)は frontmatter のデータとしては存在せず、curator の判断に宿っているだけ。これをデータにすると、(a) 昇華先ルーティングが文言ではなく型で決まり、(b) stats に「どの信号種が多いか = どの制品がボトルネックか」が出る。

実装概要:

- `add --signal context|instruction|workflow|failure`(省略時は根因行から推定、不能なら unknown。既存エントリは unknown 扱い — 後方互換)
- curator の昇華先マッピングを根因(失敗系のみ)から signal(全系)へ拡張:
  `context` → CLAUDE.md 提案 / `instruction` → rules.md(措辞)/ `workflow` → rules.md・将来はプレイブック節 / `failure` → 根因で lint・test・境界ルールへ振り分け(現行の根因ルーティングは failure 内部のサブルーティングとして存続)
- rules.md の表示を**失敗由来(守るべき制約)/ 成功由来(再現すべき措辞・進め方)**に分ける — アンチパターン置き場を新設せず、正例の出口を確保する(工作流信号の△を解消)
- capture-feedback スキル・AGENTS.md 規約4に signal 選択を1行追加

規模: 小(スキーマ1項目 + テンプレート + 文言)。
軽量性: ✔ 記録時のコスト増は選択1つ。プレイブック等の新ファイルは作らない。

### P4. `doctor` — 制品ドリフトの機械的検出

**記事根拠**: L59(定期審査: 制品が「仍然有效」か)、L81(更新されないロックファイルは安定ではなく負債。テストスイートと同じ規律で保守せよ)

棚卸し(Phase 4)は语义的な審査で、人間+curator のコストが高い。機械的に検出できる陳腐化は先に機械に見つけさせ、審査を「残った判断」に集中させる。

実装概要(`scripts/doctor.sh`、feedback-loop Phase 2 と Phase 4 の前処理から呼ぶ):

1. **ベンダ版バージョン整合**: `init.sh` が導入時に `.feedback/.harness-version` を記録。doctor がプラグイン側 `plugin.json` の version と比較し、不一致なら「`init.sh` 再実行の案内」— マーケットプレイス自動更新でプラグインだけ新しくなり、ベンダ版 `scripts/` だけ古くなる歪みの検出
2. **rules.md 参照 liveness**: ルール本文・出典詳細が言及するパス(バッククォート囲み)の存在検証。消滅した参照 = 陳腐化候補
3. **ポインタ断片のドリフト**: 導入先 CLAUDE.md / AGENTS.md 内のハーネス断片と `docs/pointer_*.md` の内容比較 → ずれていれば更新提案(init.sh の断片更新と CLAUDE.md 手編集の分岐検出)
4. **構造検査**: log frontmatter の id 一意性・status 値の妥当性(既存テストのランタイム版)

出力は「維持 / 要更新 / 破損」のテキスト。修正は既存の原則どおり提案止まり(直接編集しない)。

規模: 中。
軽量性: ✔ 四半期の棚卸しを軽くする装置であって、新規の定期作業は増やさない。

### P5. クロスプロジェクト還流 — プラグイン自身へのフライホイール

**記事根拠**: L15–17(個人の経験をチームの基盤に変える)、L87–89(飞轮は他のすべての実践の保守機構である)。ハーネスでは「チーム」を「配布先プロジェクト群」と読み替える

現状、各導入プロジェクトの `.feedback/` は孤立しており、プラグイン自身(skills / hooks / check.sh)はハーネスリポジトリ内の `.feedback/` からしか学習できない。導入先で「check.sh がスタックを検出しない」「フックが不具合を起こす」という経験(L39 の文脈信号のプラグイン版)が蓄積しても、ハーネスに還る経路は人力。

実装概要:

- `feedback_log.py export --since <date>`: 導入プロジェクトの学習を Markdown バンドルに出力(要約・category・根因・signal + check.sh の未検出スタック情報)
- ハーネスリポジトリ側で通常の `add --source agent` で取り込み、ハーネス自身の curator が昇華先(= プラグイン資産: スキル文言・hook 挙動・check.sh のマニフェスト追加)を判断する
- feedback-loop に **Phase 5「還流」**を追加: 導入プロジェクトで export → ハーネスリポジトリにコミット → プラグイン改善提案。**2プロジェクト以上での同種の再発はプラグイン修正の強いシグナル**と定義する
- 集約の自動化(同期・ネットワーク経路)は作らない。手動コピーで十分 — 記事の「軽さ」の原則(L79)を一段上の層でも守る

規模: 中(export 1サブコマンド + Phase 5 の文書化)。
軽量性: ✔ 新規インフラなし。既存の add/curator の経路をそのまま使う。

## 3. 採らない方針(記事に照らして見送るもの)

## 4. 推奨ロードマップ

| Wave | 内容 | Steps としての意味 | 依存 |
|---|---|---|---|
| 1 | **P1 + P2**(測る・共有する) | Step 4: 「測定」と「朝会/振り返り」の2つの空白を同時に埋める。P2 の議題に P1 の数字が乗るので同波が自然 | なし |
